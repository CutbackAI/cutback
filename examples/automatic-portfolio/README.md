# Let the agent compare alternatives

An independent support-ticket router chooses **billing**, **access** or **technical**. Cutback's agent prepares several model/output-token configurations, rejects a cheap constant answer, confirms a passing generated instruction and prepares an exact source change with application checks and rollback. Its 240 synthetic examples stay in 60 declared intent families, so related variants do not become independent evidence. The sample has no connection to a private application.

Start from a source checkout with Python 3.11–3.13, Git and running Docker Desktop:

```sh
uv sync --locked --all-extras --dev
uv run cutback demo --ticket-router
```

Wait for `Ready:`, open the displayed browser URL and choose **Explore sample → Inspect ticket-routing failures**. No account, API key or copied credential is needed; the demo's existing project-scoped login stays in browser memory. The temporary collector/PostgreSQL/encrypted store are real. Press Ctrl+C after exploring to remove the demo's own temporary database and encrypted objects.

The ordinary source-bound agent path uses the same `workflow prepare --for-campaign`, `campaign prepare`, finite operator and application-check adapters available to an application owner. New campaign preparation selects v3 and freezes up to four static alternatives. Native provider HTTP is intercepted by explicit synthetic transports. Its answers, usage and prices are fixture evidence, not measurements of the named real models. Inspect the complete campaign before studying the rest of the repository:

1. **Frozen economic bounds:** model/output-cap alternatives, cumulative native dollar/request ceiling, reserved instruction-search effort and complete baseline cost reference. Preparation itself executes no inference. If the full portfolio does not fit, inspect which alternatives were omitted before approval; validation and confirmation samples stay intact.
2. **Initial validation:** all frozen static alternatives use the same held-out validation cases and unchanged reference. The baseline returns all three expected labels; the cheaper constant `billing` answer fails the access/technical cases. The sample deliberately makes these alternatives fail so the reserved instruction-search path is visible. In the failed run, open **Inspect encrypted case evidence**, enter a purpose such as `owned-sample-review`, then read paired expected/actual answers. Content retention is explicitly enabled for this owned sample; it remains off by default for ordinary agent preparations.
3. **Instruction search:** only if static validation found no eligible winner and the frozen budget already reserves this stage. Candidate instructions are encrypted. The proposer receives permitted training examples and aggregate validation feedback; it never receives validation/test examples.
4. **Confirmation:** freeze one eligible candidate and compare it on untouched test families. Failure ends the campaign. Reimporting the same cases cannot reset their exposure history.
5. **Application review:** inspect the exact diff, rollback and checks on both clean source trees. The sample leaves the application unchanged and labels its decision synthetic. A source binding does not prove independent test coverage or production savings.
6. **Task economics:** the optional synthetic later-outcome walkthrough retains all campaign operation costs and separates declared assumptions from measured windows.

The existing guided `uv run cutback demo` also retains a v2 single-alternative campaign for compatibility. Preparing a **new** campaign in its Campaigns page uses v3 and shows the frozen portfolio table before approval. Saved v1/v2 campaigns resume with the original hash and order.

For an already configured owned local collector with authorized encrypted storage, the same three-label journey is available separately:

```sh
uv run python examples/improvement-campaign/sample.py --local-target . --outcomes --ticket-router
```

This advanced script leaves its synthetic project for inspection; add `--cleanup` to delete only that project. It does not supply a dashboard key or alter the local collector's authentication configuration. The guided demo above is the no-key first-use path.

For an authorized application's own source and data, follow the [complete campaign workflow](../../docs/improvement-campaigns.md). A coding agent can discover source contracts, prepare permitted examples, locate a matching baseline, derive the portfolio, run an already approved campaign, prepare the reversible change and execute authorized checks. Data rights, vendor permission, cost assumptions, paid execution and production release still need actual owner authority; the synthetic sample does not supply it.
