# Continuous quality and incidents

Source-checkout functionality; not included in the published dev5 wheel. Migration `0011` adds PostgreSQL rules, evaluation work receipts, alert windows, incidents/events, typed shared views and optional notification configuration/deliveries. Released migrations through `0010` remain immutable. Start with the [independent synthetic sample](../examples/online-monitoring/README.md).

## Evaluate outside the request

For local Compose testing, explicitly set `CUTBACK_ONLINE_EXECUTION=true` before starting/recreating the worker service. The Compose default remains false; webhook execution remains false until a reviewed private override supplies approved configuration. A direct Python worker can use `CUTBACK_PROCESS=worker` with `python -m cutback.server.boot` and the ordinary private database configuration. These are self-hosting instructions, not a production deployment performed by this project.

An administrator creates `/v1/projects/{project_id}/online-rules` with an explicit version UUID, expected previous revision, environment, typed metadata filter, event-time interval, deterministic sample rate, evaluation count ceiling and approval reference. A new version disables the previous version; it does not mutate its specification or results. Disabled old versions cannot be re-enabled over a newer version. Duplicate identical version requests return the original record. Sampling is stable for the server-assigned span identity and rule version.

This initial execution profile is **nonbillable metadata only**: observed execution status, a maximum observed span duration, or one exactly identified external boolean evaluator/source/version attached to that span. Execution success is not business success. External evaluation remains externally asserted, including when supplied by a judge elsewhere. Missing results, contradictory/multiple external results, invalid boolean contracts, evaluator errors, cancelled/incomplete execution and expired source spans remain distinct. Unsupported evaluator options and nonzero provider budgets are rejected. Cutback does not silently call a judge.

Intake adds at most one durable outbox record per new span when rules are enabled. A separate worker selects rules/samples and expands evaluation targets in bounded batches of twenty spans; it never evaluates content or calls providers in the application request. Duplicate ingest cannot create another outbox record. Retention deletes pending outbox pointers with their source spans. `CUTBACK_ONLINE_EXECUTION=true` enables the worker's separate backfill, evaluation and alert phases. All are disabled by default. An initial bounded sweep handles retained spans; subsequent ingestion handles late arrivals. A full 50,000-receipt project queue reopens backfill rather than rejecting otherwise valid telemetry. Coverage remains unknown, including while a backfill is pending. Rule limits are 50 enabled versions per environment and 1,000 retained versions per project. A rule's count reservation is durable before evaluation; expired leases may be recomputed because this profile makes no billable operation. Recomputing does not consume a second evaluation reservation. Exhaustion becomes unknown, never passed.

## Closed windows and evidence

Alert rules reference an exact online rule version. UTC event-time windows are half-open `[start,end)`, with an explicit grace delay, minimum sample size, signal, Decimal threshold and cooldown. Failure rate divides failed results by passed plus failed results; evaluator-error and missing rates use completed selected receipts. Pending/missing/error/unknown counts remain visible. A no-data or incomplete window cannot automatically recover an incident. A later qualified healthy observed window can recover it; neither state establishes full traffic health. Delayed external results are accepted until their work deadline. A terminal result is immutable; a late result after that deadline requires a new evaluation version/backfill, rather than silently rewriting historical evidence.

One open incident per alert version is deduplicated under a project/alert lock. Initial breach evidence is frozen. Acknowledge, assign and resolve transitions use incident revision CAS and immutable events. An owner is a routing reference, not an access grant. Manual resolution does not re-open the same activation window; later breaches respect cooldown. Changing an alert version leaves its old incidents for explicit review. All incident APIs enforce project scope and existing viewer/editor/admin roles.

The **Monitoring** dashboard displays rule versions, observed counts, incident state/history, retained evaluation receipts and direct trace investigation. Authorized encrypted trace content can enter the existing blind Review workflow; missing payloads are not reconstructed from metadata. Typed saved views contain only safe filters and state. Views apply to explicitly loaded pages; pagination is visible. There is no credential-bearing share URL or arbitrary stored query code.

## Optional metadata webhooks

Helm exposes `execution.online` and default-disabled `notifications.enabled`. Notifications require a **separate** `secrets.notifications` Secret: the collector receives only its registry entry, while signing key references mount only on the worker. Schema/render checks reject incomplete, duplicate, privileged-variable or shared-runtime-secret opt-ins. Configure permitted worker egress explicitly. Keep real registry/signing configuration in ignored `*.local.yaml`, environment/secret files or your secret manager; restart processes after environment-backed registry/key rotation. No cluster has been contacted by these rendering checks.

Operator destination entries also require a `project_ids` allowlist. Only those projects can discover or approve that destination. Each delivery freezes the destination hash and configuration revision; reapproval cannot silently retarget old queued receipts. Project deletion waits for an already reserved delivery attempt to finish. A total transport deadline also bounds slow response headers and TLS, not just response bodies.

No destination is configured by default. Building this integration does not authorize external messages. An operator supplies `CUTBACK_WEBHOOK_DESTINATIONS` as a private server configuration mapping destination identifiers to **exact HTTPS URLs**, one to four pinned public IP literals, and a dedicated `CUTBACK_WEBHOOK_SECRET_*` variable name. URLs, IPs, secret variable names and values never enter the public API or metadata export. Userinfo, URL query/fragment, control characters, non-443 ports, nonpublic/multicast/special transition addresses and arbitrary secret names are rejected. Use native public IPv4 or IPv6 addresses; IPv6 transition/NAT64 profiles are not supported.

A project administrator then explicitly authorizes future incident metadata delivery to an allowlisted identifier with an approval reference and current configuration revision. The server binds that approval to the exact operator destination configuration. A changed URL/address configuration blocks delivery until reapproved. Rotating the signing secret value is supported. Finally the operator enables `CUTBACK_WEBHOOK_EXECUTION=true`. The dashboard exposes approvals, disabling and delivery status. No notification is sent by merely visiting a page or creating a rule.

The qualified `httpcore==1.0.9` transport connects to the pinned public literal while TLS verifies the original URL hostname with certificate verification/SNI. It does no DNS lookup, ambient proxy/authentication, redirect following or hidden request retry. A signed JSON body contains only project/incident/alert identifiers, transition action/state/revision and window timestamps. Headers include `X-Cutback-Delivery`, `Idempotency-Key`, `X-Cutback-Timestamp` and `X-Cutback-Signature: sha256=<HMAC-SHA256(secret, timestamp + '.' + delivery_id + '.' + raw_body)>`. Receivers must verify the raw-body signature, enforce a timestamp replay bound and deduplicate delivery IDs. Authentication to your receiver is the dedicated signature, not an inherited provider/admin credential.

The durable journal reserves an attempt before sending. Delivery is at least once: a receiver can accept a request whose response is lost. The same delivery ID is retained for retries and crash recovery, up to five attempts with capped exponential delay, then dead-letter status. Non-429 4xx and redirects dead-letter immediately. Response bodies are discarded with a 64 KiB limit, socket timeouts and a bounded total read interval. There are ten destinations and 10,000 retained delivery receipts per project. A full queue records an internal audit failure and preserves the incident. Disabling cancels queued deliveries; an already reserved outbound attempt may have happened. Error responses never include remote bodies or credentials. All qualification uses synthetic TCP/receivers; no external destination has been contacted.

## Retention and limits

Delayed and backfilled evaluation completions mark durable alert windows dirty. The worker revisits their original event-time windows after grace, even when the most recent minute has no data. Per-alert cursors bound backfill to 100 receipts and re-evaluation to five dirty windows per cycle. Late breaches preserve one incident activation rather than silently disappearing or creating duplicates. Window history is available in the dashboard/API. There are ten enabled alert versions per online rule and 50,000 retained window receipts per project; exhausted history capacity is explicit, audited and never converted into known coverage.

Evaluation receipts expire with raw retention. Source-span deletion sets its evaluation link to null, preserving unknown source availability until receipt retention. Resolved incidents and their events/deliveries expire with aggregate retention; active incidents remain for triage. Configuration and typed views are exported as metadata and cascade on project deletion. Neither raw samples nor retained summaries establish unobserved denominators or missing quantiles.

This increment does not implement billable online judging, content/schema online evaluation, input distribution drift, complete labeled cohort drift, automatic rollback or later task-outcome economics. Those remain explicit work, alongside Releases 5–7. Existing approved experiment judging is a separate workflow and cannot be advertised as an online judge.

Receivers can use the dependency-free `cutback.webhooks.verify_webhook_signature` helper to authenticate the exact bytes, delivery identity and replay window. It does not parse business decisions or persist deduplication; validate the incident schema/project and atomically deduplicate the authenticated delivery ID in your own store.
