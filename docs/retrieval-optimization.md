# Optimize a real local text corpus

Source-checkout capability, not part of the published dev5 package. Git must be available on PATH for the source-bound demo and configuration/check workflows. [Executed acceptance](progress.md) is separate from this contract. This adds actual corpus retrieval to the existing experiment worker. It does not reinterpret the earlier declared RAG/tool fixtures as corpus search.

## The user journey

1. Import questions with independent answer labels under an active, purpose-scoped encrypted capture policy. Keep duplicate/customer groups together. The existing dataset importer assigns train, validation and test groups; reimporting exposed questions cannot manufacture fresh test evidence.
2. Select the corpus and the application's current retrieval settings. In **Retrieval**, upload the corpus only after confirming its rights and capture scope. The corpus is encrypted inside the frozen plan, once per plan. Metadata contains counts/settings and opaque references, not document text or an unsalted corpus digest. An approval hash is salted by a mandatory content nonce.
3. Prepare the comparison. The local generator proposes at most five distinct alternatives: smaller chunks, fewer documents, changed overlap and optional lexical coverage reranking. It does not call a proposer model, an embedding API or an application tool. The native model, instruction, output ceiling and supported request configuration stay identical across alternatives.
4. Review the exact plan hash, native request ceiling and worst-case native API reservation. An administrator approves one run. Queue it on the normal explicitly enabled worker. Every native request has its durable PostgreSQL reservation before dispatch. Unknown usage, a crash, an outage or an uncertain acknowledgement stops execution without automatic billable replay.
5. Inspect answer scores and actual contexts, not just a retrieval proxy. The dashboard shows measured context bytes and CPU time. If encrypted case retention was selected, an audited administrator can compare the actual retrieved passages and model outputs on the same question. Evaluator labels/references are never sent to the native model as retrieval context.
6. Prepare confirmation. The server selects a passing, lower-component-cost validation candidate and freezes that exact candidate, corpus, query bounds, evaluator, price contract and CPU assumption on untouched test groups. Confirmation requires a separate exact budget approval. Candidate selection does not inspect held-out answers. Changed content/settings and already consumed holdout groups are rejected.
7. Prepare a source proposal after passing confirmation. A previously inspected settings-only JSON file and the entire clean tracked Git tree must still match. The proposal contains an exact configuration diff and rollback; it does not modify the application. Run the application's reviewed checks on independent base/proposed trees, declare settings-consumer coverage, and bind those receipts with `retrieval review`. An optional local branch points only at the checked commit. No branch is pushed or production traffic changed.

The [independent application](../examples/retrieval-optimization/README.md) and the source-built `cutback demo` exercise this path without a provider key. Synthetic native replies intentionally fail when retrieval loses the answer fact. They are demonstrations, not real model accuracy or customer savings.

## Retrieval contract

`core.retrieval` depends only on the Python core dependencies. It imports no provider/server/evaluation package, opens no file and makes no network call. The offline scanner remains parse-only and does not read a corpus as an automatic scanning side effect. Explicit `retrieval query` reads selected local content and writes retrieved content to the requested output.

`cutback.local-retrieval.v1` uses character chunks, Unicode NFKC/casefold word tokenization, unique query terms and BM25 term-frequency/length normalization. The declared positive IDF is `ln(1 + (N - df + 0.5)/(df + 0.5))`, where N and df count chunks. This is an explicit implementation choice within the BM25 family described by [Robertson and Zaragoza](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf), not a compatibility claim for every search engine's analyzer or scorer. The exact recipe, normalization, frame and tie rules have a checked contract hash.

Take the best chunk per document, order score ties by opaque document UUID then character offset, optionally rerank a bounded top pool by query-term coverage, and take a ranked prefix under the actual UTF-8 JSON context budget. Passages are never silently truncated to fit. Retrieved text is JSON reference data; a fixed frame tells the model that documents are untrusted. This is not a general instruction-injection or semantic-groundedness guarantee. No document can cause Cutback to invoke a tool or fetch a URL.

Limits: 512 documents, 32 KiB UTF-8 text per document, 256 KiB total corpus text, 128–4096 characters per chunk, overlap at most half a chunk, top-k 1–12, context 1–48 KB, 4096 chunks and 262144 indexed terms. A query is bounded by its approved byte limit (default 1024, maximum 8192), 256 tokens and 64 distinct terms; a term is at most 256 UTF-8 bytes. Policies can impose smaller encrypted payload limits; oversized plans are refused, not truncated. Corpus version, settings and document identities are frozen with the plan.

The recipe also binds the runtime's Unicode database version and explicit Decimal precision/rounding. Arithmetic never inherits an application's ambient Decimal limits. Source configuration inspection carries that recipe hash. Changed normalization runtimes require matching-runtime inspection and reapproval; earlier evidence cannot silently authorize different retrieval behavior.

`deterministic-v6` requires the new retrieval contract and nonnil nonce. Existing v3/v4/v5 serialization and approval hashes are unchanged. Initially qualified execution is synchronous nonstreaming OpenAI Responses text (including its supported single text-parameter contract) and Anthropic Messages with the ordinary text executor. Existing pinned SDK and model qualifications still apply. Chat templates, native tools, vector stores, remote corpora, embedding models and learned/cross-encoder rerankers require their own adapters and acceptance; they are not supplied by this lexical contract.

## Cost and evidence semantics

Native token pricing and actual billed-call uncertainty remain in the existing canonical ledger. Retrieval CPU is measured separately using thread CPU nanoseconds; index/query wall time and scored chunks are separate counters. Index construction is included once per configuration in the sample. An optional exact Decimal USD/CPU-hour assumption rounds measured CPU up to the declared charge quantum (default one millisecond). It is a declared CPU component, not a provider invoice or a measured hosting bill.

Automatic selection requires complete native usage, a declared CPU basis, independent answer labels, sufficient samples/groups and passing quality criteria. An unknown CPU rate remains unknown; it is never assumed free. A cheaper configuration that loses answers is rejected. Memory, idle infrastructure, storage, tools, amortization at a future volume and total cost per successful business task remain unmeasured by this experiment. It does not estimate monthly savings or optimization payback from missing volume/outcome evidence.

Validation sample gates and statistical confidence are distinct. Synthetic confirmation is explicitly `synthetic_local_review_only`. An eligible sample does not become representative evidence or a production authorization. Full task economics and later outcomes retain their separate existing contracts.

## API, CLI and recovery

`POST /v1/projects/{project}/retrieval/draft` accepts the typed corpus/settings/baseline/metric/budget contract and creates an encrypted plan. Omit `candidates` to use the bounded generator. `POST .../retrieval/confirmation` derives exactly one candidate from a completed validation run. Both return ordinary plans, with the existing approval and queue APIs. `GET .../experiments/plans/{plan}/execution` reconciles a lost queue reply without posting another run. A consumed approval never queues twice.

`POST .../retrieval/{confirmation_run}/proposal` requires administrator scope, an audited purpose, current capture authority, complete confirmation accounting and fresh holdout lineage. It returns only the numeric settings/source binding and decision scope. Viewer metadata access cannot read corpus, encrypted cases or proposals. Existing content expiry/revocation, policy export/delete and project cleanup apply to the encrypted plan and retained samples. No new relational content table or migration is introduced.

Use `cutback retrieval --help` for inspect, draft, confirm, query, proposal, patch and review commands. Local patch/review JSON is externally executed evidence, not independent server attestation. Applying a patch with Git newline conversion can alter the expected bytes; use a byte-preserving checkout (`git -c core.autocrlf=false apply ...`) and verify the exact proposed hash/tree through application checks. A review is rejected if any unqualified file changed or a branch points elsewhere. Declared consumer coverage is an owner assertion, not an inferred complete dependency graph.
