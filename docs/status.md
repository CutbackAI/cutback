# What works and what remains

Updated 28 October 2026. Cutback is a pre-alpha product with tested, bounded workflows. It is not a complete competitive platform or a validated business. [Executed acceptance](progress.md) records the exact artifacts, checks, failures and limits; [the baseline](market-baseline.md) records remaining requirements.

## Choose the right installation

| Installation | Available scope |
|---|---|
| PyPI `0.1.0.dev5` | Offline scanner, native observation, collector/PostgreSQL/dashboard, support-desk demo and the earlier source-bound evaluation/change workflow. Use the version-pinned README instructions. |
| Current GitHub source | Also includes workflow/session tracing, import and blind review, prompt versions/releases, online evaluations/incidents, synthetic agent/RAG execution, task economics, bounded instruction campaigns, application-check discovery and finite outcome observation. Follow each source example's installation instructions. |
| Native modern-text follow-up | [PR 32](https://github.com/CutbackAI/cutback/pull/32) is merged after installed-package qualification and all ten required hosted checks. This adds explicit request/price contracts, not universal model support. |

A source merge does not update the PyPI wheel. New source commands require a source-matched installation and collector; do not mix them with an older wheel and assume compatibility.

## What the automatic workflow does

For qualified source and permitted examples, the agent can prepare source/data contracts, a frozen bounded search, candidate generation, validation and separately approved untouched confirmation. It can discover supported application checks, prepare independent base/proposed workspaces and an exact instruction/model/output-cap diff with rollback. An approved finite observation policy can compare later declared outcome windows and prepare a rollback review when they regress.

The independent [campaign application](../examples/improvement-campaign/README.md) exercises that path with synthetic native responses. Model support, source shapes, check commands and evidence coverage are explicit contracts. Unsupported dynamic source, unapproved content or unknown costs cause abstention; they do not become successful improvements. The workflow does not deploy changes.

## Engineering still required

1. **Gateway breadth and reliability:** the working source implements a separately enabled, finite text-gateway contract with virtual keys, shared budgets and no uncertain replay ([scope](gateway-budgets.md)); exact package qualification and public acceptance are tracked in [PR 33](https://github.com/CutbackAI/cutback/pull/33). Additional providers/surfaces, streaming, configurable reliability/fallback behavior and operational acceptance remain unfinished.
2. **Broader automatic improvements:** evidence-driven strategy selection, retrieval/tool/compression/batch optimization, learned routing and additional source/framework adapters. The current instruction search and heuristic routing do not provide all these strategies.
3. **Broader evaluation:** generated criteria and real-data scenarios, qualified application/tool isolation and simulation, broader adversarial/guardrail integrations, and the documented modality/cloud specialties.
4. **Operational qualification:** evaluator/worker/gateway capacity, intended clean-host deployment and recovery modes, remaining collaboration/provisioning journeys, and their complete dashboard lifecycles.
5. **Release convergence:** make a separately versioned release containing the accepted source workflows, qualify its final archives and complete its publication gates. The QA artifacts used during development do not replace the published wheel.

These are implementation requirements, not requests for a maintainer to finish the engineering. They remain visible in the baseline until their user journeys and acceptance gates pass.

## External evidence still required

Observed first-use trials must show that an unfamiliar developer can complete and explain the sample. Separately authorized application trials must test real task quality, complete cost attribution and later outcomes. A task-matched comparison must establish an advantage over the incumbent. Customer adoption, willingness to pay, production reliability and fundraising are not established by synthetic tests or feature count.

There is no additional account setup required to continue the current engineering. Paid provider calls, production deployment, customer outreach and customer claims require their own authorization. Private application source, identity and findings stay outside public examples, history and distribution archives.
