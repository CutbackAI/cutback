# Application outcomes, task costs and improvement receipts

Working source increment for Release 6; qualification and publication status are recorded in [progress](progress.md). This is not the complete autonomous optimizer or launch qualification. [Independent native-SDK sample](../examples/task-economics/README.md).

## Declare the business result

`POST /v1/ingest/task-outcomes` accepts 1–100 strict `cutback.task-outcome.v1` records through a project/environment-scoped ingest key. Analysts can use `POST /v1/projects/{project_id}/task-outcomes?environment_id=...`. Viewer keys can read but cannot write. Each record declares nonzero task/result UUIDs, the actual trace ID, workflow/service/release, aware task time, success/failure/unknown/error, source/version and evidence basis. No arbitrary attributes, explanations, tool arguments, documents or payloads are accepted.

HTTP/SDK success is not business success. A business event, human review, deterministic check or model assessment remains externally asserted and explicitly identified. Revise an outcome with a new result UUID and an exact `expected_previous_revision`; task target/release/time are immutable. A trace can be allocated once per environment, preventing double charging two tasks for one trace. Same-body result replay is idempotent; changed identity bodies, stale revisions and partial conflicting batches roll back. Limits are 100,000 tasks, 200,000 revisions and 100 revisions per task/project scope.

For optional background export, construct `cutback.instrumentation.task_outcomes.TaskOutcomeExporter` with the full loopback/HTTPS ingestion endpoint and scoped token. Explicitly `emit(TaskOutcomeInput(...))`, then bounded `flush`/`close` at lifecycle boundaries. Supply your actual OTel trace ID and an explicit application result; the exporter installs no tracing hooks and infers no result. Its bounded queue drops on saturation/outage, has no disk spool/automatic retry, follows no redirects and reports content-free health counters. An enqueue acknowledgment is not a delivery receipt. Preserve each result UUID when explicitly resending uncertain metadata delivery. Default SDK observation and raw-content capture behavior are unchanged.

## Preserve unknown costs

`GET /v1/projects/{project_id}/task-economics` requires an environment and at most a 30-day window within 90 days; narrow workflow/release filters before exceeding 10,000 tasks. `task-outcomes` provides bounded UUID pagination and a declaration watermark. Reports use one repeatable database snapshot; a declaration watermark freezes revisions, not future telemetry or retention. Live calculations state this explicitly.

Cost joins use exact project/environment/trace identity and canonical native attempts in preference to external OTel mirrors. Physical retries still cost money. An observed attempt must match a retained span or retained parent and have an observed wall-clock start within that span. Native duration is monotonic elapsed time; it cannot manufacture an absolute UTC end. Missing/unfinished roots, inconsistent graphs, unlinked attempts, identity mismatches and graph truncation prevent complete declared task cost. Only 1,000 spans per trace and 100,000 spans per report are inspected; truncation stays visible. Structural consistency does not prove complete capture.

`expected_native_attempts` must match priced observed attempts. Evaluation/judge/unknown-purpose traffic cannot be silently counted as application cost. Tool, retrieval, compute, hosting and other components use nonnegative Decimal USD values with 12 decimal places. Missing prices stay null. `other_costs_declared_complete` explicitly attests that the submitted component list is complete; an empty list counts as zero only under this assertion. Native rates are modeled, other prices externally asserted, and billing is unverified.

The cost-per-success numerator includes failed-task spend. Unknown/error outcomes, incomplete cost components or missing success denominators prevent a complete sample metric. A declared independent `expected_tasks` count must also match before the window metric is reported. None of these attestations establish population coverage, statistical independence or production savings.

## Freeze and compare

Analysts can `POST task-cost-snapshots` with a unique request UUID, exact window, optional filters/watermark and expected count. Frozen receipts bind all submitted revisions, retained evidence, coverage, calculation time and a SHA-256. They do not change after late observations. Creation is idempotent, limited to 1,000 tasks/four MB per receipt and 1,000 receipts per project. Paginated listing returns brief metadata; a separate scoped GET reads an individual full receipt.

`POST improvement-observations` compares two distinct frozen releases of one workflow/service/environment with no reused tasks. An optional source change must be a scoped source-diff proposal; its hash and owner-attested release linkage are retained, without implying deployment verification. An unlinked comparison is labeled as such. The supplied bounded unique list of experiment run IDs uses canonical cumulative PostgreSQL request/cost counters, including failed runs; SDK evaluation observations are never added again. Legacy unknown coverage, in-flight/uncertain calls and omitted known predecessor runs cannot become a complete optimization total. Training, tooling, engineering and other one-time costs need separate explicit components/completeness. The owner-declared run set cannot prove there were no unreported external costs.

The descriptive decision rejects a cheaper-but-worse declared outcome, inadequate sample, incomplete costs, unknown future volume or a horizon that does not repay the declared optimization cost. A favorable result can only prepare independent confirmation. Break-even and net benefit are forecasts under owner-declared future successful-task volume; uncontrolled windows do not establish causation, independent quality or realized savings. Actual inference still needs a separately approved frozen plan and pre-call ledger. Nothing in these endpoints deploys or changes traffic.

`POST search-effort` computes an offline search envelope from explicitly declared conservative unit opportunity, volume, complete proposer/per-candidate upper costs and owner cap. Unknown or too-small opportunities abstain. The suggested cap is rounded down to ledger precision and bounded by the declared opportunity fraction. The response authorizes no paid call. Native dynamic candidate generation and broader strategy execution remain unfinished.

## Lifecycle and acceptance

Additive migration `0014` preserves released migrations through `0013`. Scoped compound constraints and project locks protect identity/CAS/quota mutations. Project metadata export includes task revisions, frozen receipts and improvement observations; deletion removes them before restrictive source-change/snapshot references. Raw metadata retention removes old tasks/revisions/observations. A referenced cost snapshot remains until its live improvement observation expires, then becomes eligible for pruning. Retained receipt totals never reconstruct missing quantiles or capture coverage. A populated downgrade is refused until explicit export/deletion.

Acceptance uses real PostgreSQL, actual pinned SDK synthetic transports, authenticated HTTP/dashboard/mobile/axe, concurrent replay/conflict, unknown prices/outcomes, failed-task spend, stale UI responses, canonical optimization costs and retention/export/delete. See the actual passing/failing checks in [progress](progress.md), rather than treating these API contracts as proof of qualification.
