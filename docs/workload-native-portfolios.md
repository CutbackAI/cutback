# Prepare a trial from the workload the application sent

Source-checkout feature under qualification. Published PyPI dev5 does not
include this workflow. Use matching source CLI and collector versions, and
read the [acceptance record](progress.md) before adopting a release.

The agent can now put qualified model/output alternatives and an exact-cache
candidate in the same frozen native experiment, using a current source-matched
workload assessment to qualify the cache hypothesis. This does not complete
selection across routing, retrieval, compression, prompt generation and training.

## Start with the independent application

The [new v4 campaign extension](improvement-campaigns.md), under qualification,
also combines this fixed cache control with native alternatives and conditional
prompt search under one complete-task economic envelope. Its separate
[cache-first sample](../examples/improvement-campaign/README.md) uses ordinary
agent preparation and verifies both source trees and rollback. Generated native
instructions do not inherit the cache window's opportunity forecast.

The working source also adds a complete
[fixture-only walkthrough](../examples/workload-portfolio/README.md), under
qualification: `cutback demo --workload-portfolio`. It observes an independent
application, assesses repeats, compares alternatives, confirms the selected cache
and verifies both source trees and rollback. Its explicit native-fixture plans
cannot run through a live-provider worker. Runtime caching stays disabled and
the real-quality gate remains closed. No provider credential is needed.

The pending-trial example below is a separate path for an already running
owned collector. It stops before inference approval.

Use the existing owned loopback collector and encrypted profile worker setup in
the [request-reuse example](../examples/request-reuse/README.md). Keep the
administrator credential in the process environment. From the source checkout:

```sh
python examples/request-reuse/demo.py --endpoint http://127.0.0.1:8080 \
  --source-workload --prepare-trial --keep-source ../cutback-owned-example
```

The destination must be new. The command creates a separate committed synthetic
application with labeled cases, observes eight real SDK calls through a closed
synthetic HTTP transport, and models three potential source-window hits. It then
prepares a pending trial without making or queueing target inference calls.
`--prepare-trial` retains the collector project and source checkout for review.
Its connection file stores destination metadata; the credential stays in the
environment. No private application or deployment is needed.

Expect `synthetic_native_calls: 8`, `paid_provider_calls: 0`,
`pending_workload_trial.phase: PLAN_READY`, `provider_calls: 0` within that trial,
and `approval_required: true`. The dashboard shows the pending exact plan in
Experiments. The source and its ignored journal remain in the requested folder.
Inspect the local continuation with:

```sh
cutback workflow status --target ../cutback-owned-example
```

This example stops before inference approval. An ordinary enabled worker can
spend real provider money. For a complete no-cost native/retrieval demonstration,
use `cutback demo --joint-model-retrieval`. The automated native/cache acceptance
in `tests/integration/test_agent_cache_workload.py` separately exercises actual
SDK parsing, PostgreSQL, cold run namespaces, confirmation, both application
trees, owned runtime activation, rollback and authenticated browser evidence
through intercepted synthetic transports.

Delete the retained example project through the collector's project controls
when finished. Keep or remove the independently created source folder separately.

## Use a permitted application window

First follow [source-matched profiling](source-workload.md). Only a complete,
retained, qualified native Responses window can support automatic cache trial
preparation. The caller must explicitly provide the cache freshness reference,
TTL, retention/invalidation authorization and justified decimal operation-cost
bound. Repeated text alone is insufficient.

With the same collector connection and clean committed application, use the
installed `workflow prepare --help`, permitted independently labeled examples,
`--automatic` and `--exact-cache-contract PRIVATE_FILE`. Rights, metric minimum
and maximum native spend/requests remain explicit. Preparation rechecks the
canonical assessment instead of trusting a saved local JSON receipt.

The frozen `workload-native-portfolio-v1` binding records that exact assessment
and cache contract. The collector checks its project, source, baseline, metadata
census, prices, current capture policy and expiry at creation, content reads,
approval, queueing and before execution calls. The plan cannot outlive the
assessment. Changed or missing evidence fails closed. A correctly rehashed
client-edited receipt is insufficient.

The portfolio has at most five alternatives. If its upper bound exceeds the
owner's budget, automatic preparation removes native alternatives from its
deterministic prefix while retaining the workload-qualified cache candidate.
It records the qualified/prepared counts and any reduction. It never shrinks
the examples or quality criteria to make the trial fit. If even the remaining
trial does not fit, it stops before uploading a plan.

The original explicit native search remains available for separately reviewed
hypotheses. The older synthetic-only fixture path does not invent an observed
workload and cannot be executed by a live provider worker.

## Confirm and review

After explicit authorization, approve the exact validation hash through
`workflow continue`. Poll that same run after an uncertain acknowledgement.
Choose a candidate only from its recorded cost and quality results; an eligible
cache hypothesis can still lose to a model change or fail quality.

```sh
cutback workflow confirm --target APP_ROOT --candidate CANDIDATE_KEY \
  --max-usd 5 --max-requests 200 --purpose-reference owned-confirmation
```

The request ceiling is illustrative: review the actual untouched-test count and
repetitions. Insufficient budgets fail before saving a confirmation intent.
A lost nonbillable reply reconciles the same UUID, candidate and budget. The
new confirmation hash requires its own approval. An uncertain billable call is
never automatically replayed.

After confirmation, the existing source proposal path prepares a model diff or
an opt-in native-cache helper with a forward patch and exact rollback. Native
requests stay unchanged for an exact-cache candidate. Caching remains disabled
until an explicitly configured private runtime scope is supplied. Run application
checks on both source trees before review; configuring a malformed enabled scope
fails instead of silently dispatching an uncached request. No command deploys.

## Read the economics honestly

The report and Experiments dashboard count known validation and confirmation
spend, including rejected candidates and declared cache operation upper costs.
They show how many identical repetitions of the retained native window would
cover that trial subtotal. That is an assumption about the same window, not a
forecast of future traffic or a production payback claim. Large repetition
counts are exact decimal text, preserving values beyond JavaScript's safe
integer range. Incomplete family billing keeps the count unknown.
The opportunity belongs to the qualified cache hypothesis. A model-only winner
keeps the eligibility evidence but has no inferred payback from that cache window.

Full task costs, human review, deployment, hosting and realized savings remain
unknown. Explicitly marked synthetic transports retain a synthetic disclosure
on every candidate and cannot pass the ordinary real-quality gate. Synthetic
fixtures establish software behavior, not customer model quality or savings.
